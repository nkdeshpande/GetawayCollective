GC.SYSTEM · Decision Register · 02 Aug 2026

Twenty-four decisions,
five tracks, one dependency.

Every defect from the build-status assessment, stated as a decision you can take. Each one gives the defect with its evidence, the options with a recommendation, the implications of each, and what it depends on.

Two things are worth knowing before you read further. Track A is four small decisions and the public site is launchable at the end of them — three need nothing you do not already have, and the fourth needs one free-tier service. Almost everything else terminates at one decision: D-05, the database. Twelve of the remaining twenty name it as a dependency.

One recommendation inverts what you would expect. D-02 recommends NOT fixing the security advisories, because the automated fix downgrades Next.js by six major versions and no patched version exists. The reasoning is set out in full.

How to use this

Each decision has an id (D-01) and lettered options (A1, A2). Reply with the ones you want — D-01 A1, D-02 B1, D-05 E2 — or say approve recommended to take every green option.

Sizes are relative effort, not calendar time: S is under a session, M is a focused day, L is several days, XL is a body of work with its own decisions inside it. I have no basis for estimating your team's velocity and have not pretended otherwise.

Nothing here is started. Nothing is irreversible until you choose.

D-02

Ten security advisories, and the automated fix is a trap

P0Size S
Defect

1 critical, 4 high, 5 moderate. But npm audit fix --force proposes installing next@9.3.3 — a downgrade of six major versions that would delete the App Router and every route in this build.

The advisory range for Next is 9.3.4-canary.0 – 16.3.0-preview.7. Today's latest release is 16.2.12, which is inside that range. There is no patched version to upgrade to.

critical vitest dev-only · UI server arbitrary file read high vite dev-only · path traversal in optimized deps high postcss build-time · XSS + sourceMappingURL path traversal high sharp libvips CVEs · reachable only via next/image high next transitive: postcss + sharp npm audit fix --force -> "Will install next@9.3.3, which is a breaking change"
Options
B1Recommended

Accept all five with written rationale, pin the review, and re-evaluate when a patched Next ships.

Implication: each is genuinely low-risk for this application, and the rationale is specific rather than hand-waving. vitest and vite are devDependencies and the Vitest UI server is never started in CI or production. postcss runs at build time over CSS this repository authors — an attacker has no input to it. sharp's libvips CVEs are reachable through next/image processing untrusted remote images; this app serves local imagery and has no remote loader configured.

Recording the reasoning matters more than the outcome: an accepted risk with a stated basis can be re-examined, a silently ignored one cannot.

B2

Upgrade Next to 16.x anyway.

Implication: buys nothing — 16.2.12 is inside the advisory range — and costs a major framework upgrade with its own regression surface across 107 generated pages.

B3Destructive

Run npm audit fix --force.

Implication: installs next@9.3.3. The build would not survive it. Listed only so nobody reaches for it later.

Depends on

Nothing.

No database is provisioned

P0 · HINGESize S–M
Defect

Two migrations are written; neither has been applied. This blocks the email magic link, the grant table, the sixteen-stage passport, notifications, search, and every Wave 8 module. Google sign-in is the sole exception — an OAuth handshake with a JWT session needs no adapter.

migrations/0000_productive_scorpion.sql institutional schema — never applied migrations/0001_naive_puck.sql 5 auth tables — never applied
Options

The installed driver is postgres (postgres.js), which speaks to all of these through a pooled connection string. No application code changes whichever you pick.

E1 · NeonRecommended

.env.example already names it, so the intent is on record. Serverless-native with scale-to-zero, a generous free tier, and database branching that maps onto Vercel preview deployments — a preview can get its own data without touching production.

E2 · Supabase

Also Postgres, also free-tier viable. Brings auth, storage and realtime you do not need — Auth.js already owns identity here, and adopting Supabase auth would mean unwinding this session's work.

E3 · Vercel Postgres

Tightest integration, one dashboard, one bill. Now a paid product, and it is Neon underneath.

E4 · Self-hosted

Full control and data residency in India, which may matter for a SEBI-adjacent platform. Costs you backups, patching, connection pooling and an on-call expectation.

Implications regardless of choice

Set DATABASE_URL, run npx drizzle-kit migrate, and the magic link, the grant table and lib/session.ts all begin working with no further code. Residency is worth a deliberate thought rather than a default: E1 and E3 offer regional placement, E4 guarantees it.

Depends on

Nothing. Everything else depends on this.
