Nine criticisms,

Severity 1 · Structural

Nothing is served. This is a specification, not a product.

There is no app/, no pages/, no route of any kind. The chain runs unbroken from constants/ufr.ts through Zod contracts and the Drizzle schema to 396 lines of DDL — and terminates there. next dev would start and serve nothing.

The one interface that exists is a single self-contained HTML file. It is not the product; it is a proof that the design system can be built.

app/ does not exist pages/ does not exist routes 0 served nothing
Severity 1 · Unverified

The interface has never been rendered. Not once.

GC-ASSEMBLIES.html is 155 KB across thirteen assemblies. Every claim made about it — that the layouts hold, that the tabs work, that the piston fills, that the ground inversion reads as intended — rests on parsing the file, executing its render functions headlessly, and computing contrast arithmetically.

The browser preview tooling timed out on all three attempts this session. No human and no browser has seen this file. Arithmetic cannot catch a collapsed grid, an overlapping element, a font that failed to load, or a layout that breaks at 380px.

verification used parse · headless render · computed WCAG never performed visual inspection · browser render · device test
Severity 2 · Coverage

Eleven of twenty-eight assemblies exist only as specification.

The registry is the deliverable people read as complete, and it is complete. The build is not. Eleven assemblies have sections, rules and corrections recorded and no implementation — 32 sections and 40 corrections that exist only as text.

Correction to an earlier count. This finding first read "fifteen, including all three chrome components and both regions". That was wrong: chrome and regions are built as helper functions rather than screen entries, and my audit only counted the latter. The header, spine, footer and hero viewport are all built and invoked. The real figure is eleven.

Severity 2 · Coverage

The aperture system covers 11% of the objects it governs.

Apertures are the tier that decides what each vantage may see — the mechanism the whole disclosure model rests on. Three objects have one: Property, Distribution, Resolution. Twenty-four do not, including Investor, Commitment, Agreement, OwnershipPosition and CapitalCall — every object carrying personal or financial data.

Worse: the time and admin vantages have no aperture at all, yet AS-25 sits at time and AS-13 sits at admin. Two built screens operate at vantages the disclosure layer does not describe.

objects with an aperture 3 of 27 vantages with an aperture gateway · space · capital · member vantages WITHOUT time · admin ← both have built screens
Severity 2 · Proof

Thirty state transitions, fourteen irreversible, tested by example.

The transition table is declared as data, which is exactly what makes exhaustive testing possible — and the tests never iterate it. They exercise chosen paths. An irreversible transition quietly acquiring a reverse route is the failure mode this layer exists to prevent, and nothing currently walks every edge to check.

This is the same class of defect as the Member Law firing on acceptance instead of settlement, which two independently-correct declarations produced and only a cross-check caught.

transitions 30 marked one-way 14 (reversible: false) iterated by a test no
Severity 2 · Proof

Money is exact by construction and unfuzzed by policy.

Every amount is a bigint in minor units scaled 10⁴, and allocate() uses largest remainder so splits sum exactly. That is the right design. But three edge cases have no test: allocation of a zero total, allocation across a single weight, and behaviour at very large values. There is no property-based testing anywhere in the repository.

Exactness by construction is a strong claim. It deserves a stronger check than eleven hand-picked examples.

allocate(0n, …) untested allocate(x, [1n]) untested very large values untested fast-check / fuzz absent from package.json
Severity 3 · Declared, unbuilt

Five design subsystems exist only as constants.

Charts, density modes, terminal mode, print and PDF, and email templates are all declared with real rules — six named charts, four density modes, a print spec. None has an implementation. The risk is not the absence; it is that a declared subsystem reads as a delivered one when the registry is the thing being reviewed.

Severity 3 · Enforcement

Six invariants are constitutional text and nothing else.

Thirty-five of forty-one reach a field or a capability. These six do not, and two of them — Identity Invariance and Transfer Is Additive — are precisely the guarantees a secondary transfer would violate first.

Severity 3 · Assurance

Every accessibility claim in this system was made by me, checked by me.

The contrast work is real: every shipped pairing was computed against its actual ground, including blended opacity, and four separate failures were caught and fixed this session. But it is arithmetic on hex values. No axe run, no pa11y, no screen reader, no keyboard walkthrough by anyone but the code that wrote it.

Contrast is the one part of accessibility that arithmetic can settle. Focus order, announcement quality, whether aria-current lands where a screen reader expects it, whether the piston is operable by switch control — none of that has been tested at all.
