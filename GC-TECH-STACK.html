Getaway Collective · what runs the platform

Five accounts. One authorization model.

Getaway Collective governs the vehicles that own properties; it does not run buildings, and it holds no equity in what it governs. The stack follows the same discipline: the fewest relationships that cover every capability, with the constitution — routes, rights, capabilities — staying in this repository rather than living in a vendor's dashboard.

The five accounts

four to run the platform · the fifth the day a deposit is taken

Each is chosen for fit against what already exists — the Drizzle migrations already target Postgres, the route table already derives access from vantage, the authority model already declares 33 rights. A product that slots in without an adapter written around it beats a better product that needs one.

Clerk authenticates. It does not authorize.

Clerk ships organizations, roles and permissions as a product feature. None of it is used. This platform already has a complete authorization model: 33 rights, 8 roles, grants carrying a scope and an expiry, one authorise() entry point with no default-allow branch, and a linter that refuses a right no role carries.

Two authorization models is worse than either alone — not because they would disagree on day one, but because six months later the question "why could this person do that" has its answer split between a dashboard and a repository, and only one of them is in version control.
  • Clerk owns: who someone is — the session, MFA, device list, sign-in, recovery. It answers one question and hands back a stable identity.
  • The repository owns: everything after that. resolveSubject() maps the Clerk identity to a Subject, and the existing guard decides access exactly as it does today.
  • The rule: no Clerk role or organization name appears anywhere in this codebase. If one does, the boundary has broken.

Already closed by code in this repository

why the account count stays at five

Not deferrals. Each of these is a capability a platform this size usually buys, already implemented here with the file that does it. Listed with what replacing it would cost — the honest reading is that keeping it is cheaper than migrating it, not that it beats a dedicated product on features.

Why forms stay native

react-hook-form plus the Zod schemas already in the repository, rather than a form-builder service. Accreditation collects identity documents, PAN, address, tax residency and source-of-funds evidence — routing that through a third-party form product makes that vendor a data processor for the most sensitive material this platform will ever hold. A data-processing agreement, a residency question, a sub-processor list to monitor, and their breach becomes a notification obligation here.

In exchange, it would buy field validation that constants/validation.ts already declares, with copy already checked against 17 tone prohibitions. No capability is bought — only exposure.

Payments: Razorpay

India-domiciled platform · Indian residents · rupee deposits

The vehicles are Indian LLPs. Partners are Indian residents settling in rupees. Razorpay is built for that transaction from the ground up rather than adapted to it.

Not needed yet — and the trigger that changes that

a deferral with no trigger is a decision nobody made

Every line names the condition under which it returns. If a condition is met and the capability is still absent, that is a fault — which is the point of writing the trigger down instead of saying "later".

The rule that keeps five accounts safe

Business logic calls a capability — "notify a partner", "persist", "take a deposit" — never a product. lib/commands.ts declares 35 capabilities, each naming the right it requires and the events it emits, and a linter refuses one that emits nothing. A vendor is an implementation of a capability; swapping one is an adapter change.

Concretely: Razorpay sits behind the payments capability, Resend behind notifications, Clerk behind resolveSubject(), Vercel Blob behind media registration. None of those names belongs inside a business rule.

Before any of this is provisioned

  • Data residency. Clerk holds identities, Neon holds accreditation records, Vercel holds request logs — three processors handling personal data under the DPDP Act. Confirm what each actually guarantees on region, not what the marketing page implies, before the first accreditation record exists. Moving personal data across regions afterwards is materially harder than choosing correctly now.
  • Who holds the deposit. The flow takes ₹50,000 on the platform and completes the balance offline. Whether that money is ever held by Getaway Collective or passes straight to the vehicle changes the regulatory shape of the platform, and it changes the Razorpay integration pattern.
  • Clerk or WorkOS. Clerk fits an individual partner, which is what a ₹40,00,000 unit implies. WorkOS becomes the right pick the moment an institutional investor needs SSO against their own identity provider — a family office running Okta cannot use a magic link. Ask the question before the first institutional offering opens; switching afterwards is real work.
  • Authentication is unimplemented. resolveSubject() currently returns ANONYMOUS and every guard fails closed — correct for now, and the first thing Clerk touches.

What five accounts do not cover

No error tracking, no uptime monitoring, no log retention beyond platform defaults, no feature flags, no analytics. Defensible at prototype scale. Not defensible at the first real partner — error tracking should be account six before launch, not after the first incident, because its entire value is in already having it when something breaks.
