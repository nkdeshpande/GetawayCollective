Three overlooked features
are one missing layer.

CRM, CMS and the IRIS chat were treated as three product categories, so they read as three projects. They are not. They are three faces of the relationship layer, and GC already owns its spine — 55 event types, an envelope carrying actor, object and causing command, and a projection doctrine that says every read model is a pure fold over events.

That reframing changes what gets built. None of the three is a system to buy or bolt on. One is a projection nobody has written. One is an authoring path, not a CMS. One is an engine that cannot run until the other two feed it.

Why each looked missing, and what is actually absent

CRM is not missing — it is unprojected. Every consequential command already publishes an event with actorId, objectType and causedBy. A CRM in GC is a fold over that log scoped to a person. ADR-0007 already requires projections to be pure functions of a readonly event array. Nobody has written this particular fold.

CMS is not missing — it was refused, and the refusal was right. Copy lives in content/ as TypeScript so vocab-lint and voice-lint can read it. A conventional CMS puts words where those linters cannot reach, which is a regression dressed as a feature. What is genuinely absent is an authoring path that still passes the gates.

IRIS is not missing — it is unfed. Eleven contracts exist with governed outputs, human gates and prohibitions. AI-102 emits an "Investor Context Update" and there is nothing to update. AI-101 may speak only from "the public approved projection" and no approval workflow exists. An agent with no memory and no sanctioned vocabulary is a demo.

The order is forced, not chosen

The instinct is to build IRIS first because it demos well. It has to be last, and the reason is in your own contracts rather than in general engineering caution.

ContractWhat it needs that does not existConsequence of building it first
AI-101"Public approved projection"No approval workflow, so "approved" means whatever the model read
AI-102Output: "Investor Context Update"Nothing to update. The output object has no home
AI-103Handoff carrying "intent, questions, documents, commitments"None of that is recorded, so the handoff carries nothing and UX-07 fails at the moment it matters
AI-104"Own entitlement + source refs"No entitlement record; the agent guesses or refuses

So: interaction record → approved content → engine. Each stage is independently useful, which is what makes the sequence safe to stop halfway.

Capability 1

The interaction record — "CRM"

R-01

Every touch, folded per person, from the log you already write

Spine exists
Design · the job to be done

Investor Relations opens one person and sees: what they asked, what was sent, what they signed, where they stalled, what is owed to them and by when. Today that lives in an inbox and somebody's memory.

The constitutional framing matters more than the feature list. A CRM usually stores opinions about people. This stores acts — each already carrying an actor, a command and a timestamp, because E-01 made that mandatory before anyone wanted a CRM.

Design · what it must not become
  • Not a second identity. The L2 sheet is explicit: use one Investor before and after settlement. No Contact, no Lead, no Person object.
  • Not a new object at all. "Task / notice / activity — capability/event artifact, not L2 object." It is a projection.
  • Not free-text opinion. A note field becomes an unaudited record about a person, which is exactly what disclosure classes exist to govern.
Build · the first slice

One fold and one surface. No schema beyond what the event store already needs.

lib/projections.ts relationshipOf(investorId, events) -> { stage derived from the lifecycle events, never stored interactions[] every event where this identity is actor or subject owed[] obligations opened and not closed lastContact the most recent outbound notice with a delivery record stalled time in stage against the gate's target ETA }

Surfaced at PAR-110 (the partner record) for the Office and folded into MEM-200 /activity for the member's own view — the same fold, two apertures, which is UX-02 holding rather than being asserted.

Launch · how you know it worked

Investor Relations answers "where is this person and what do they need" without opening email. And the member sees the identical history at /activity, redacted but never restated.

The trap

A CRM is where UX-08 usually breaks

Internal notes, deal stages and probability scores are administrative machinery. If the fold is shared between apertures without a disclosure class on every field, the member's own activity view will eventually show them what the Office thinks of them.

Close it by giving each projected field a DisclosureClass — the enum landed in constants/taxonomies.ts — and filtering the fold by aperture at the edge, not in the component.

Capability 2

The authoring path — "CMS"

R-02

Publishing that a non-engineer can do and the gates still refuse

Deliberate refusal
Design · the real requirement

The ask sounds like "we need a CMS". The requirement is narrower and better: someone who does not run a terminal must be able to publish a Journal entry, a progress update or a property description, and the vocabulary and voice rules must still run on what they wrote.

This build has already demonstrated why that clause is load-bearing. Writing the contact page an hour ago, vocab-lint refused the word "booking", then refused "concierge", then refused a sentence containing an operating-company noun. A CMS that bypasses those checks would have published all three.

Design · the shape that survives the constitution

Not "a CMS". An authoring surface whose publish button is a gate run.

author writes ─▶ draft stored (Evidence artifact, not an L2 object) │ ├─ vocab-lint forbidden terms ├─ voice-lint brand voice, no hedging └─ disclosure class set, aperture chosen │ approval by a named right (content.publish) │ ▼ EFFECTIVE — and only now may IRIS quote it

Note what this gives you beyond publishing: it is also the thing that makes AI-101's "approved claims only" enforceable. The CMS and the AI guardrail are the same mechanism seen twice.

Build · the first slice
  • Journal entries only. One content type, lowest risk, no figures.
  • Draft → review → effective, using the Evidence state taxonomy already declared (RECEIVED → CLASSIFIED → VERIFIED → EFFECTIVE → SUPERSEDED).
  • The linters run server-side on submit and the failures are shown to the author in their own words, not as a build log.
Launch · how you know it worked

A Journal entry goes live without a deploy, and an attempt to publish one containing a forbidden term is refused with the reason — the same reason the linter gives an engineer.

The trap

Do not let content become a second source of truth

The moment an author can type a yield, a valuation or a date into a page, the platform has two numbers for one fact and no way to know which is current. T-14 already states it: public content is an aperture projection of approved Property and evidence, never a second source.

Close it by making figures uninsertable. The authoring surface offers a reference to a canonical value; it does not offer a number field.

Capability 3

IRIS — the engine, last

R-03

Contracts exist. Give them memory, a vocabulary and a mouth.

Contracts declared
Design · what is already settled

More than people expect. Eleven contracts with triggers, input scopes, governed output objects, mutation levels, human gates, cross-agent rules, provenance requirements and named prohibitions. Both agents hold requestableRoles: [], so neither can acquire a right — enforced by the shape of the type, not by policy.

What is not settled is the model provider, and that is correctly separate.

Design · the one thing to get right

The output object is the product, not the chat. A conversational reply that leaves no record is exactly the "invisible agent action" FIX-10 exists to prevent. Every consequential IRIS turn produces a typed, sourced artifact — an Interaction, a Context Update, a Handoff Package — and the chat is a view over those.

Build the artifact first and the transcript second. Doing it the other way produces a product that is impossible to audit and pleasant to demo.

Build · the first slice
  • AI-101 only — the public question. Smallest scope, lowest stakes, no member data, no investor projection.
  • Retrieval restricted to content in EFFECTIVE state from capability 2. If it is not approved, IRIS cannot see it.
  • Every answer carries source ids. No source, no answer — refusal is a valid output.
  • Escalation writes a Handoff Package and hands to a named human. Not a mailto.
Launch · how you know it worked

Ask it something the approved corpus does not cover and it declines and offers the human path, rather than answering. The refusal is the acceptance test, not the answer.

The trap

The name is a constitutional decision, not branding

"Concierge" is forbidden outright — an operating-company concern belonging to the Operating Partner. And "Investor Relations" is a constituted internal office that can request compliance_office, which holds accreditation.grant. Naming the agent after it would give the thing that may hold no authority the name of the office that may accredit.

It also breaks the handoff: AI-103 escalates "to a named human (IR handoff)". If the agent is Investor Relations, that reads as Investor Relations escalating to itself.

IRIS is the system name. Label the member-facing control "Ask about this place" if the codename feels cold — presentation, not identity.
